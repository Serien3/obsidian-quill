# 架构规范与边界设计

当用户希望讨论、设计或固化一个软件系统的架构规范时使用。目标是和用户一起找出少数几条值得长期固守的结构性决定，说清每条决定的边界在哪里、为什么存在、将来在什么条件下该改。

你在这场讨论中的角色是架构对话伙伴：提问、给出候选、指出矛盾、把用户模糊的直觉压成明确的陈述，并在用户想得太多或太少时给出自己的判断。最终取舍由用户做。

这份规范会同时被人和编码 agent 阅读与遵守。写规范时记住 agent 的三个特点：它没有跨任务的记忆，每次运行都像入职第一天；它会忠实复制仓库里已有的模式，包括坏的；它的吞吐量远超人的审阅能力。规范能否被它读懂、能否对一段具体代码明确判定是否违反，决定了规范是否真的存在。

## 先建立几个观念

这些观念贯穿整场讨论。遇到具体分歧时，回到这里找依据。

### 架构的存在理由是变化

一个写完就不再改的系统不需要架构，怎么写都行。架构之所以存在，是因为系统会被反复修改、扩展、部分替换，而修改的代价取决于结构。所以评价一个架构的标准不是它今天看起来多整齐，而是明天一个需求进来时，它让这个需求付出多大代价。

有韧性的架构有一个可感知的性质：一次改动的代价与改动本身的大小成正比，而不是与整个系统的大小成正比。做到这一点靠的是把变化关在局部。一个新需求理想情况下落在一个模块内部，稍差落在一条边界上，最坏才是穿过所有模块。边界放在哪里，本质上就是在预测变化会从哪里来：预期会变的东西两侧要有边界隔开，预期一起变的东西不要被边界切开。

没有架构能对所有变化都有韧性。保护一种变化通常以牺牲另一种变化为代价，比如为“随时换存储”预留的隔离层，会让“存储与业务一起演化”变得更慢。所以讨论时要和用户一起挑出最可能的几种变化，让它们便宜；对不太可能的变化，只要求架构不把门焊死，不要求便宜。为不太可能的变化提前付费，就是过度设计的本质。

与此相关的是可逆性。架构决定里只有少数是难以回头的：数据的所有权与存储形态、系统的物理拆分、对外承诺过的协议。讨论时间应当按可逆性分配，难回头的多想，易回头的快决、写明、错了再改。

### 早定拓扑，晚定领域与抽象

过去推迟架构约束是理性的：人脑里有隐性的架构图，小团队短期内不需要显式规则；把规则写明并让所有人遵守本身有成本；漂移是线性积累的，来得及在评审里纠正。当 agent 参与编码，这三个前提全部失效：它没有隐性的图，只能看到写下来的东西；写明规则的成本已经远低于不写的代价；漂移以每天几个 PR 的速度复制已有模式。

于是约束要提前，但提前的只是其中一部分。几乎不依赖业务知识的东西应当早定：模块之间的依赖方向、允许的边的集合、横切关注点进入系统的通道与几条最要紧的横切约定。跟着产品走的东西应当推迟：具体的领域清单与领域边界、为想象中的需求预留的抽象层、为尚未出现的关注点预留的入口。

“不做架构”得到的不是零架构，而是偶然架构：第一个出现的模式会被默认复制并锁定。

### 韧性来自约束可改，不是约束少

架构能否承受需求变化，取决于当架构需要改时，你是否知道它在哪些地方被依赖。写明的约束是可改的：改一条陈述，就知道哪些地方要跟着动。只存在于人脑和习惯里的约束是改不动的，因为没有人知道它在哪些地方被默认了。

衡量一条约束是否可承受的标准是可减去性：如果将来发现它错了，能否在一个改动里把它整个删掉。目录约定加一条依赖方向规则可以删，织进代码各处的框架层删不掉。优先选可减去的约束。

### 本质复杂度与偶然复杂度各有各的机制

本质复杂度来自问题本身，架构的任务是把它分解成可以独立推理的块，这由模块切分、连接与拓扑来承担。偶然复杂度来自实现者的习惯，agent 是偶然复杂度的高效生产者：重写已有的工具函数、猜测数据形状、把文件写到几千行、日志格式各写各的。这类东西与业务模块无关，不管加多少模块它都一样，所以由横切关注点的约定来管。讨论时把两类问题分开，不要用一套机制同时管两件事。

### 规范规定的是性质，不是过程

架构规范描述系统必须始终满足的性质，而不是达成这些性质的步骤。判别方法是问：这条规则说的是“什么必须成立”，还是“应该怎么做”。“外部数据必须在边界处完成形状校验”是性质；“用某个库做校验”是过程。“存储层不得感知 HTTP”是性质；“存储层采用某种模式”是过程。

性质可以落在很细的粒度上，比如单文件大小、日志是否结构化、类型命名。粒度细不等于微管理，只要它描述的是一个可核对的状态。反过来，哪怕是组件级的规定，若它在规定先做什么再做什么，也是在微管理。

### 中央执行边界，局部允许自治

把系统当作一个平台组织来治理。中央只关心少数几件事：边界、正确性、可复现性。边界之内，解决方案如何表达，由实现者自由决定。从架构组件到程序代码这一段路，是刻意留给实现者的自由空间。

判断一条候选规则属于中央还是局部，问一个问题：如果两个互不沟通的实现者在这件事上做了不同的选择，系统会坏吗？会坏，或者会让系统无法被整体推理，它就属于中央，要写进规范。不会坏，只是风格不同，它就属于局部，哪怕你有偏好也放手。按这个标准，依赖方向、横切关注点的入口、边界上的数据契约属于中央；一个函数怎么拆、用哪个库、内部数据结构怎么组织属于局部。

所以一份好的规范更像“允许的边加禁止清单”，而不是操作手册。它说清什么不能依赖什么、什么只能从哪个口进来、什么被刻意排除，然后停下。实现出来的代码可以不符合某个人的审美，只要它正确、可维护、对下一次阅读它的人或 agent 可读，就达标。中央管得少而严，局部才能动得快。

### 可判定性是规则的门槛

一条架构规则若不能用一句话说清、不能对一段具体代码判定它是否违反，就要么改写到能判定为止，要么明确降级为“建议”并接受它会被遗忘。不可判定的不是约束，是愿望。

## 从一个想法到一个系统：架构在各阶段的分量

架构规范随项目阶段改变分量。讨论开始时先确认用户处在哪一段，因为同一条建议在不同阶段的对错不同。

**只有一个想法，准备做最小的东西验证它。** 这一阶段最大的风险不是架构不够，而是偶然架构被锁定。该做的事很少但必须做：按最粗的粒度切出模块，定下依赖方向，定下一两条最要紧的横切约定。不定领域边界，不建抽象层，不为扩展预留任何东西。这套东西加起来是几个目录名和几句话，它的作用是让后面每一次改动都不必再争论文件放在哪里。

**验证有效，准备做广度扩展。** 这是架构真正开始回本的阶段，也是最容易出问题的阶段。广度扩展意味着许多功能被并行加入，往往由多个 agent 同时做。此时领域边界开始浮现，可以逐步固定；在 MVP 阶段反复出现的模式可以开始提取；早期口头或隐性的约定该正式写进规范。衡量这一阶段架构好坏的直接指标是：并行进行的改动是否互相碰撞。碰撞多，说明切分的轴不对，或者边界划在了一起变的东西中间。

**系统已经成熟，架构主要在维护。** 此时规范是组织记忆，大部分约束已经稳定。工作重心转为回顾：哪些规则不再有理由，哪些边界已经名存实亡，哪些当初推迟的决定现在条件成熟了。

无论哪个阶段，有几个信号意味着架构该被重新审视：某个模块被几乎每次改动触碰；同一种模式第三次出现；某条规则被频繁绕过或申请例外；一个本应便宜的变化场景实际上很贵。遇到这些信号，不是打补丁，而是回到切分本身。

## 一份架构由什么构成

下面是看一个架构的几个视角。模块、连接、拓扑回答系统由什么组成、如何相连、整体是什么形状；约束回答这些东西在实现时必须满足什么；横切关注点回答那些不属于任何一块却贯穿所有块的事怎么办。

其中约束没有自己的领地。一条约束总是某个模块的约束，或某条连接的约束：一个模块的描述由它的职责和它的不变式共同构成，一条连接的描述由它的交互形式和它刻意排除的东西共同构成。所以无论是讨论还是落成文档，约束都写在它所约束的东西旁边。

### 模块：从业务世界进入计算世界的第一次切分

功能模块是设计者对问题做的第一个决定：业务领域里的概念，以什么样的单元进入程序。这次切分决定了后面所有讨论的词汇表，也决定了本质复杂度被分到了哪些格子里。

一个好的模块有三个性质。它的职责能用一两句话说清；它能被一个人或一个 agent 在一次任务里整体读懂；它能被整体替换而不惊动外部。三者里最常被忽略的是第二条，它直接决定了模块的粒度上限。

描述一个模块时，职责只是一半。另一半是它刻意不做什么、向外承诺什么：永远不做某类 I/O，永远不知道某个协议，永远不失败而是返回结果加错误列表。这些就是挂在这个模块上的架构不变式。只写职责的模块描述说了模块在做什么，没说读者可以依赖什么。

切分的轴通常有两条：按业务领域纵切，按技术职责横切。多数系统两者都有，先按领域纵切，再在每个领域内部按职责横切。检验切分是否合理的朴素标准是：一起变的东西放在一起，分开变的东西分开放。切分的轴应当对准预期的变化方向。

各功能模块的架构不变式可以统一，也可以各异。有的系统给所有领域一套相同的架构模型，例如每个领域内部都分成固定的几层、代码只能沿一个方向依赖。这是把同一条不变式写一次，让每个模块继承，各模块只写自己的例外与补充，好处是实现者走到任何一个领域都看到同样的形状。另一类系统的模块本身性质迥异，比如一条处理流水线上的各个阶段各有完全不同的内部结构，这时每个模块各写自己的不变式。判断依据是模块之间的相似度，能提取多少就提取多少，不为了能写成一条而把不相似的模块压成同一个形状。多数系统是混合的：模块之间的边界规则统一，模块内部各写各的。起步时内部往往还看不清，先定模块之间的关系，模块内部的不变式随着它成形再补。

讨论模块时值得问的问题：这个模块被整个删掉，系统哪些部分不受影响？它拒绝做什么，这个拒绝换来了什么？哪两个模块总是同时被修改，它们是不是应该合并？哪个模块的职责说不清，是不是切错了轴？

### 连接：边界两侧各自承担什么

模块本身不产生耦合，耦合产生在连接处。连接描述模块之间如何交互，它是整份规范里最需要精确措辞的部分，因为所有跨模块的假设都藏在这里。

交互的形式本身携带假设。函数调用假定同步与同进程；消息假定异步与可能的丢失；共享数据结构假定双方对所有权与可变性达成一致；网络调用假定失败是常态。选择形式就是选择这些假设，规范要把它们说出来。

每个模块要区分供外部使用的接口和内部实现。外部只能依赖接口，内部实现可以随意变。更进一步，要明确哪些模块是对外的 API 边界，哪些模块明确声明“现在不是、将来也不是”。后一种声明同样是承诺，它让实现者知道哪里可以放心重构。

每条边界要说清四件事：两侧各自负责什么；通过什么形式交互；哪些依赖或行为被刻意排除；为什么这样设计。这四件事就是这条连接的约束。第三件最重要也最容易漏。重要的边界往往表现为某物不存在，比如某个目录里从来没有某类 import，某个类型从不穿过某条线。这种“不存在”从读代码几乎推不出来，只有写下来，它才真的存在。第四件是约束的生命线，没有理由的规则会在第一次不便时被绕过，而且理由是将来判断这条规则是否该废除的唯一依据。

讨论连接时值得问的问题：如果边界一侧被整个替换，另一侧需要改什么？两侧对失败的理解一致吗？有没有哪条边是“顺手”加上去的，没有人能说出它为什么存在？

### 拓扑：连接之后的整体形状

模块经连接连起来，就得到一张图。拓扑讨论的是这张图的性质，而不是节点的内容：依赖有没有方向，允许的边是否有限可枚举，横切关注点从哪里进入，哪些边同时是物理边界。

依赖方向要能用一句话说清。能用一句话说清的规则，人能记住，agent 能在任何一个文件里直接套用。允许的边应当是有限集合，列出来，其余一律禁止，而不是写“合理的依赖都可以”。这把原本看不见的边界变成可枚举、可判定的东西。

拓扑有一个重要的性质：它通常与领域无关。问一句“如果明天换一个完全不同的业务，这套拓扑还能用吗”。能，说明它是可以提前固定的那类东西。不能，说明它掺了领域假设，要把领域假设剥离出去推迟决定。

物理分布是拓扑的另一面。进程、服务、部署单元的划分决定了哪些边界同时是网络边界。网络边界是另一个类别的边界：它会失败、有延迟、两侧版本可能不同步。跨越它的契约要比进程内的边界严格得多，这往往是序列化、版本兼容、稳定性承诺这些话题的来源。物理拆分也是最难回头的决定之一，进程内的边界将来可以升级为网络边界，反过来要难得多，所以起步时倾向于逻辑上分开、物理上不拆。

讨论拓扑时值得问的问题：图里有没有环？外部世界通过几个口进入系统，每个口能否收敛成一个？哪条边一旦出现就很难拆，是不是应该从第一天就禁止？

### 约束：写在模块与连接旁边的“必须”

前面说的模块与连接描述系统“应该”长什么样；约束，也叫架构不变式，说的是这个样子在实现时“必须”成立。它是从组件设计通往代码实现的那座桥：规定实现必须落在什么架构模型之内，不规定在这个架构模型之内怎么写。这一节讲的是怎样给前面的模块与连接写约束。

**约束依附于它所约束的东西。** 一条不变式总是挂在一个具体的模块或一条具体的边界上，说明它守护的是谁。看起来全局的规则也不例外：“只有一处知道某个密钥”的真正内容是指定那一处是谁，并宣告其余所有模块都没有这项知识，它挂在那一处上。依附让约束可以被定位：改某个模块的人在模块旁边就能看到它的全部约束，评估一条约束该不该废除时知道去哪条边界重新看。收进独立章节的约束，改代码时没人会去翻。

**每条不变式都是一笔交换。** 不变式本质上是放弃一种自由，换取一种能力。禁止某物存在，换来的可能是独立推理、可并行、可整体替换、可对外承诺稳定、可以安全重构。比如“解析永远不失败，解析器总是返回结果加错误列表”，放弃的是在解析阶段抛错的便利，换来的是下游所有代码不必处理解析失败这条路径；“一棵语法树只覆盖一个文件”，放弃的是跨文件的便利表示，换来的是所有文件可以并行解析；“只有一个模块知道外部协议”，放弃的是在任何地方直接读写协议的便利，换来的是协议变化只伤一处。写不变式时，把换来的东西写出来。这就是它的理由，也是将来判断它该不该废除的唯一依据：当那种能力不再被需要，或者有了更便宜的来源，不变式就该退场。一条说不出换来什么的不变式，多半只是某人的习惯。

**最重要的不变式往往是“某物不存在”。** 代码能自己说清它做了什么，却永远无法说清它刻意不做什么。某个模块从不做 I/O，某个类型从不穿过某条线，某个层从不感知运行环境，这些事实在代码里没有体积，读一万行也推不出来，它们只有被写下来才存在。所以写约束时优先用否定形式：不得、永远不、只有谁知道。肯定形式的规则容易在不知不觉中滑向规定过程，而否定形式天然只划边界，边界之内自由不受影响。

**刚性放在结构上，自由放在表达上。** 实现者在边界严格、结构可预测的环境里最有效，agent 尤其如此。可预测意味着：允许的依赖是一个有限集合，实现者走到任何一处都能判断自己可以依赖什么；横切的事务从一个显式的口进入，而不是每处各自摸索；边界上的数据形状被声明，而不是靠猜。这些地方的刚性是乘数，一旦写明处处生效。但刚性必须停在结构上。要求“外部数据必须在边界处完成校验”是结构，规定用哪个库校验是表达；要求“这一层不得感知存储”是结构，规定这一层内部用什么模式是表达。深入到表达层面的刚性不会换来一致性，只会换来绕过。

**不变式要少而久。** 只写不太可能变的东西。一条每个月都要修订的不变式不是不变式，它是还没想清楚的设计。集合保持小，因为每个常规贡献者都要读完并记住它。

讨论约束时值得问的问题：这条规则禁止了什么，换来了什么？它挂在哪个模块或哪条边界上？给一段违反它的代码，能否一眼认出？两个实现者在这件事上选得不同，系统会坏吗？在什么条件下它应该被废除？

### 横切关注点：不属于任何模块，却贯穿所有模块

任何切分都只能沿一条主轴进行。沿主轴切出模块之后，总有一些事务沿着另一条轴变化，在每个模块里都要被再次面对。这些就是横切关注点。它们不是设计失误，而是切分的必然副产品：主轴选得越好，被挤到另一条轴上的东西就越清晰。

横切关注点有一个共同的性质：它与业务模块的数量和形状无关。再加十个模块，测试策略基本不变，错误仍然要传播，日志仍然要可查，数据仍然要在边界处校验。所以它是规范里最稳定的部分，也是一个项目的策略与品位真正落脚的地方。模块与边界随产品演化，横切约定一旦定下，往往贯穿项目的整个生命。

识别横切关注点的方法，是设想每个模块由互不沟通的人独立开发，然后问：有哪些问题每个人都得各自回答一遍，而答案若不一致整个系统就会出问题？有哪些性质是运维者、测试者、未来的阅读者要求处处一致的？有哪些事情穿过了系统与运行环境之间的边界，比如时间、随机性、配置、外部进程？有哪些坏习惯是实现者在每个模块里都会重犯的，比如手写已有的工具、基于猜测的数据形状往下建、让一个文件无限膨胀？错误如何传播与转换、并发与取消如何传递、事务归谁所有、配置从哪里进入、可观测性如何贯穿、安全决定在哪一层做出、生成物如何对待、测试策略是什么、测试边界允许替换什么、共享工具与手写代码的取舍，诸如此类都是常见的候选，但清单要从用户的系统里发现。

横切关注点的设计有一对固有的张力。没有规范时它们各写各的，系统里出现五种错误处理风格和三种日志格式。规范过度时它们变成无处不在的框架层，每个模块都被迫背上一套基础设施。走出这对张力的办法，是对每个关注点回答三件事：从哪里进入，入口最好唯一且显式；统一约定是什么，哪些必须处处一致、哪些允许局部自由；禁止什么，哪些层绝不直接触碰它。

判断“是否必须一致”的依据是有没有下游消费者。日志若被查询工具消费，格式必须统一；错误若要跨边界转换，错误的分类必须统一；针对坏习惯的约定，消费者是下一个读这段代码的人或 agent。没有消费者的一致性是负担，纯审美偏好不进规范。做法上倾向一个窄的入口加一条否定规则，而不是一套基础设施。关注点尚未出现时不预留入口，出现时再加。一条被频繁绕过或申请例外的约定比没有更糟，实现者会学会绕过它，然后对其余规则也失去敬畏。

讨论横切关注点时值得问的问题：这件事如果各模块各做各的，谁会最先受伤？它的一致性由谁消费？把它的入口收窄到一个，哪些模块会抱怨，抱怨的理由成立吗？

## 好规范的特质

讨论结束前，用这些特质核对产出：

- 短。每个常规贡献者都要读完它，所以要能在十分钟内读完。只写不常变的东西。
- 每条规则一句话能说清。说不清的规则，要么没想清楚，要么在微管理。
- 多数规则是否定形式。肯定形式的规则往往在规定过程。
- 没有一条规则漂浮在全局。每条不变式都写在它守护的模块或边界旁边，或者明确属于某个横切关注点。
- 每条规则有理由、有废除条件。没有理由的规则会被绕过，没有废除条件的规则会在过时后继续束缚系统。
- 每条规则可判定。给一段具体代码，能说出它是否违反。
- 规则之间互不矛盾。读者遇到两条冲突的规则时行为不可预测，往往是两边各违反一半。
- 不规定实现。没有具体库名、模式名，除非那本身就是一条边界契约。
- 每条规则可减去。能在一个改动里删掉的约束才是可承受的。
- 没有为想象中的需求预留的东西。没有空的插件接口、没有只有一个实现的抽象、没有“将来可能用到”的层。
- 对预期的变化有交代。最可能的几种变化各自落在哪个模块或哪条边界上，说得出来。

## 头脑风暴的角度

在给出候选方案前先探索。挑与用户系统相关的问。

找该固定的东西：

- 哪些东西一旦变了，整个系统要重写？那就是要用约束固定住的。
- 系统里有哪些“只允许一个地方知道 X”的事实？
- 如果某个模块被整个替换，哪些东西应该不受影响？这划出了边界。
- 哪类错误在没有约束时会在每个模块里被重犯？这是横切约定的候选。
- 哪些决定难以回头？它们值得多花讨论时间。

找该推迟的东西：

- 哪些东西三个月内大概率会变？不要固定它。
- 哪些抽象现在只有一个实例？先不抽，等同一模式反复出现再提取。
- 哪些横切关注点现在还不存在？不预留入口。

用变化场景试探切分：

- 列出三到五个最可能发生的需求变化，逐个追踪它会触碰哪些模块、穿过哪些边界。一个变化若穿过所有模块，切分的轴大概率错了。
- 列出一两个不太可能但影响巨大的变化，只检查架构有没有把门焊死，不要求它便宜。
- 有没有某个模块出现在每一个变化场景里？它可能承担了不该承担的职责。

检验候选方案：

- 把它删掉要动多少地方？
- 换一个业务它还成立吗？成立是拓扑，不成立是领域假设。
- 本质复杂度被它分解了，还是被它搬了个地方？
- 它是在标出一堵墙，还是在预先决定未来的形状？

## 过度设计的警惕线

用户常担心早定架构会引入不必要的复杂性，反而限制未来的走向。这个担心针对的是两类东西中的一类：

- 结构不变式只规定什么不能依赖什么、什么只能从哪里进来。它是减法，不增加代码量，随时可以删。它标出的是墙的位置，不规定墙内的房间怎么布置。这类东西应当早定，它让未来的改动有迹可循，是韧性的来源。
- 投机性抽象是为想象中的需求预建的插件系统、泛型层、多余的接口、可配置一切的框架。它是加法，织进代码各处，删不掉。它预先决定了未来的形状，而未来几乎从不按预想的形状到来。真正限制未来走向的是它，在任何阶段都应当拒绝。

几条经验性的红线：同一模式反复出现之前不提取抽象；不为“将来可能多实例、多后端”预建层，等它成为真实需求时，有明确的依赖方向在，重构是可控的；若一条规则需要一段话才能解释清楚它的例外，它很可能不该是规则；若一条约束的理由是“以防万一”，它不该进规范。

## 讨论流程

按这个顺序推进，每步产出一小段可以写进规范的文字。用户已有明确判断的地方直接采纳。

1. 摸底。项目处于哪个阶段、规模预期、谁在写代码、已有的隐性架构共识。阶段决定后面每一步的分量。
2. 识别本质复杂度。这个系统难在哪里：领域规则、状态与并发、外部集成、数据量与性能。架构围绕最难的那件事组织。
3. 列出变化场景。和用户一起写下最可能的几种需求变化，以及一两种不太可能但影响巨大的变化。这张清单是后面检验切分的尺子。
4. 提出候选切分。给出一到两种模块切分、连接与与拓扑，说明各自固定了什么、推迟了什么，并用变化场景逐个试探。若各模块共享同一架构模型 / 分层结构，在这一步定下并只写一次。
5. 逐模块、逐边界展开。每个模块说清职责和它的不变式（拒绝什么、承诺什么、换来什么）；每条边界回答四件事。
6. 发现并规范横切关注点。每个关注点回答进入路径、统一约定、禁止什么。
7. 审查。用过度设计的红线逐条检查，删掉投机性的部分；给每条约束核对理由与废除条件。
8. 整理产出。按下面的骨架输出。

## 产出骨架

骨架只有四部分，顺序是从整体到局部再到贯穿全局的事。组织方式可以随系统调整，不变的是每条约束写在它所约束的模块或边界旁边。

```
# 架构规范

## 整体视图

- 系统解决什么问题，核心输入与输出，围绕哪种本质复杂度组织
- 各功能模块与组合连接关系，用一张流程图/时序图/活动图等业务流程图描述系统流程
- 若各功能模块共享同一架构模型 / 分层结构，在这里写一次，并声明适用范围：依赖方向规则，横切关注点从哪里进入，物理分布（如适用），用一张或几张架构图描述，方便设计师、开发人员快速理清信息架构
- 预期的变化：最可能的几种变化各自落在哪里；不太可能但影响巨大的变化，架构如何不把门焊死

## 模块与边界

- 每个功能模块一节：职责 / 对外接口与内部实现的界线 / 架构不变式（拒绝什么、承诺什么、换来什么、何时废除）
  - 与该模块相关的边界紧随其后：两侧职责 / 交互形式 / 刻意排除 / 理由
  - 若各业务功能模块并不共享相同的架构模型，则给出各功能模块架构模型上的规范（不变式）
  - 共享相同架构模型的模块只写自己的例外与补充

## 横切关注点

- 逐项：进入路径 / 统一约定 / 禁止事项 / 理由

## 待决事项

- 推迟决定的领域边界、需要在某个条件触发后回头看的问题
- 讨论中被拒绝的抽象与预留，以及拒绝的理由，防止同样的提议反复出现
```

## 讨论时的姿态

- 提方案时同时说出它固定了什么、推迟了什么、将来如何删掉、对哪几种变化便宜。
- 讨论一个模块时，同时说它拒绝什么；讨论一条边界时，同时说什么被刻意排除。约束与它所约束的东西在同一口气里说完。
- 用户提出的每条约束，替它说出“禁止了什么、换来了什么、挂在谁身上”，再问一句“两个实现者在这件事上选得不同，系统会坏吗”。说不出换来什么的，帮用户压清楚或放弃；不会坏的，建议放回局部。
- 用户想固定领域边界或预建抽象时，问一句“现在有几个实例”，然后给出判断。
- 用户想跳过架构直接写 MVP 时，说明偶然架构的代价，尊重最终决定，并把最小的那套（切分加依赖方向）作为折中提出。
- 各要素按用户系统的实际分量投入。某个要素在这个系统里不重要，一句话带过即可。
