# 架构规范

本项目增强 Obsidian 原生 Markdown 编辑体验，不另造编辑器、数据库或私有内容模型。本文记录 Module 的职责、Interface 的承诺及依赖方向；需求与验收结果不在本文维护，测试入口见 [测试说明](testing/README.md)。

本文中的 Invariant 是改动必须保持的属性，不指定 Module 内部的实现方法。文档不是自动检查的替代品；现有保障及缺口见下文。

## 总体设计

原生 Markdown 是内容的事实来源。编辑作用于宿主打开的编辑器；交互状态、语法分析缓存和渲染映射不成为另一份可编辑文档。插件停用后，核心内容仍可阅读、编辑。

Essential complexity 主要在三处：Live Preview 可见内容与源码选区的对应、焦点与异步事件下的来源有效性，以及自定义编辑对 Markdown 结构的保护。它们应集中在有明确 Interface 的 Module 中，而不是散落到各个按钮和入口。

```text
main.ts：装配与注册
  ├── formatting：选区格式交互、自定义下划线
  └── insertion：插入交互、动作及目标有效性
          │ 声明所需的宿主 Interface
          ▲
        host：提供满足这些 Interface 的 Adapters
          │
          ▼
        Obsidian 宿主
```

功能 Module 直接使用真实 CodeMirror 状态、视图和事务，不再包装一套通用编辑器模型。功能拥有宿主 Interface，`host` 依赖这些定义，装配入口将 Adapter 交给功能；功能不反向依赖宿主 Implementation。

## Module 与 Interface 承诺

### formatting：选区格式交互与下划线

`src/formatting/` 承接工具栏交互、选区身份、自定义下划线编辑及渲染文字到源码的映射。对外以 `quillToolbar` 注册编辑器扩展；宿主能力由 `FormattingHost`、`SelectionQueries` 提供。

- 原生格式动作由宿主执行。格式展示态查询不取代宿主编辑语义，不用本地 Markdown 解析结果重新实现或限制原生命令。
- 自定义下划线使用可独立保留的 `<u>…</u>` 源码。结构安全检查与事务生成归下划线 Module 所有；不支持的结构拒绝编辑，不猜测修复。
- 下划线编辑保留正文、选区方向与可独立撤销的操作语义；交互调用者不自行拼接标签。
- 渲染下划线映射必须由宿主 widget 对应的准确源码位置建立，并核对渲染文字。不以全篇搜索同名文字猜测位置；不能可靠映射时不编辑。
- 工具栏及高亮菜单属于各自的编辑器视图。失效的手势和旧菜单回调不能接管新的交互；视图销毁时释放监听和浮层。

下划线内部的解析、结构规则与缓存属于 Implementation，不扩展为通用格式引擎。其 Depth 来自把结构安全和源码修改集中在小 Interface 后面，而不是把解析细节暴露给交互调用者。

### insertion：插入动作与菜单交互

`src/insertion/` 承接动作身份、展示信息、来源目标有效性及菜单交互。对外以 `lineInsertMenu` 提供扩展与打开入口；宿主能力由 `NativeInsertion` 提供。

- 菜单点击与打开命令遵守同一目标资格规则：单一空选区、可编辑状态、有效来源编辑器及受支持的正文区域。资格检查不移动光标、不扩选整行、不预先改写内容。
- 一次插入绑定打开时的来源编辑器、文档与选区。执行前必须仍有效；恢复焦点可能触发同步变化，因此宿主执行前再次核对来源与可用性。
- 目标失效或命令不可用时停止，不转向另一个编辑器，不重试，不自行写入 Markdown 作为后备。
- 一次确认最多执行一个原生命令。执行后文档和选区由宿主决定，不恢复打开菜单前的旧选区。
- 菜单、搜索、键盘选择与目标提示属于单次交互；关闭或销毁后，保留的旧事件不能继续编辑或关闭新交互。

编辑目标的有效性规则归编辑行为所有，菜单负责呈现与交互生命周期；新增入口不能复制一份独立的目标规则。

### host：Obsidian 接入

`src/host/` 是 Obsidian 协议进入功能的 Seam，负责原生命令调用、宿主状态查询、上下文订阅及原生菜单。

- 原生命令 ID、非公开编辑器能力、宿主 token 名称与 widget DOM 协议留在这里，不泄漏给功能调用者。
- 宿主查询返回功能词汇中的事实或明确的不可用结果；来源身份缺失、语法无法取得或能力不存在时，不猜测可编辑上下文。
- 执行针对请求的来源编辑器，不因当前活动编辑器变化而改写其他笔记。
- `watchContext` 返回释放函数，释放后不再通知该次订阅；高亮菜单返回可重复调用的关闭函数，关闭过程允许同步触发隐藏回调。
- 不在宿主接入中维护第二套编辑文档，也不把宿主协议细节带入插件装配。

失败表现由各 Interface 定义，不强行统一为一种返回形式：格式 Adapter 提供失败通知；插入返回成功或失败，交互失效可静默结束。能力失败不等于获准切换到另一种编辑实现。

### main：装配

`src/main.ts` 创建生产 Adapters、注册扩展与宿主命令，不承载格式规则、目标有效性、菜单状态或非公开宿主协议。装配保持浅而直接，不引入仅为转发调用而存在的额外 Module。

## Module 之间的 Invariant

- `formatting`、`insertion` 不导入 `host` 的 Implementation。生产和测试通过功能拥有的 Interface 接入宿主能力，使行为可在真实 CodeMirror 中独立验证。
- 两个功能不读取或修改对方的交互内部状态。当前通过编辑器选区、焦点和上下文变化协作，不设全局交互状态中心。
- 功能词汇与展示信息由功能拥有；宿主命令映射由 Adapter 拥有。不能从原生命令表反推产品动作定义。
- 功能可以使用 CodeMirror 类型；当前插入 Interface 也使用 Obsidian `Editor` 作为来源身份，但功能不借此绕过 Adapter 调用宿主编辑能力。类型依赖不等于授权访问宿主协议。
- DOM、浮层和坐标以所属视图的 document/window 为准，不假定主窗口就是当前编辑窗口。资源生命周期不长于所属视图或单次交互。
- 异步或延迟回调执行前须确认仍属于原交互且视图未销毁；宿主焦点恢复等可重入调用后，不能假定调用前上下文仍然成立。

Interface 应隐藏 Essential complexity，给调用者提供 Leverage，并让修改集中在一个地方形成 Locality。是否拆分 Module，以可观察行为和实际变化为依据，不以文件行数或层数为依据。

## 验证与保障

| 约束 | 当前保障与限制 |
| --- | --- |
| Interface 类型与宿主能力形状 | TypeScript 严格检查；类型断言不能证明非公开宿主协议成立 |
| 来源隔离、失效停止、单次执行、无编辑后备 | 宿主接入单测与公开交互测试；不代替真实宿主验证 |
| 菜单、选区、下划线、布局与生命周期行为 | 真实 Chromium 和 CodeMirror 集成测试；人工 token 树与 widget 不证明宿主实际协议 |
| 原生命令语义与真实 Live Preview | 独立 Obsidian 验收；不属于 `npm test`，单版本结果不代表所有支持版本 |
| Module 依赖方向、宿主协议集中化 | 当前主要由审查保障，尚无专门的静态架构检查 |

测试以 Interface 的可观察行为为主，不为访问交互内部状态而扩大生产 Interface。宿主协议测试使用独立预期值，不读取被测命令映射作为预期。新增测试应守住属性，而不是锁定某一种 Implementation。

日常验证为类型检查、测试、构建，三者分别执行；构建成功不代表测试通过。本文不记录测试数量或最新通过状态，历史报告不作为当前通过证据。

真实宿主自动化使用独立配置、可丢弃 vault 并核验路径；`obsidian_test-vault/` 是受保护的真实体验环境，不是破坏性测试目录。具体操作遵循 `AGENTS.md` 与测试说明。

## 演进与刻意暂缓的决定

- **不抽象通用编辑器。** 当前目标就是增强 Obsidian/CodeMirror；只有出现明确的第二种编辑运行时需求，才重审该 Seam。
- **不建立通用动作注册、菜单框架或全局交互管理器。** 新入口先复用已有行为 Interface；出现真实重复变化且能减少调用者知识时，再提取共享 Module。
- **不恢复通用 Markdown 格式器。** 原生格式继续交给宿主。新增自定义编辑须有明确需求与内容安全承诺，不能充当宿主失败后的后备路径。
- **不预设格式与插入共享同一种交互会话。** 两者的焦点、失效和执行过程目前不同；先分别守住契约，再以真实复用需求决定是否共享 Implementation。
- **不维护项目旧 Implementation 的兼容层。** 删除过时路径，但不能据此破坏用户内容可移植性或忽略已声明的宿主支持范围。

改变 Module 职责、Interface 承诺、依赖方向或上述暂缓决定时，同步更新本文；普通内部重构不需要重写架构。发现源码与本文不符时，应明确报告差异，而不是默默把当前偏差改写成新的架构决定。
